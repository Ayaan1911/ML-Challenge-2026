# Runbook

Every command runs from the repo root with the venv active (`.venv\Scripts\activate` on Windows,
`source .venv/bin/activate` elsewhere). Runtimes were measured on MA's laptop: i5-12500H (16 logical
cores), 16 GB RAM, no GPU. Everything under `data/cache/` and `logs/` is regenerated by these
commands and is not committed.

## 0. One-time setup

```
py -3.11 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
REM copy the organizer dataset into dataset\train and dataset\test
python -m pytest -q                       REM ~5 s
```

## 2. Normalization cache

| Command | What it does | Time | Peak memory |
|---|---|---|---|

A file is rebuilt only when `src/normalize.py` has changed, so **after merging AM's normalize.py,
rerun `python -m src.norm_cache dev train test`** and then every blocking step below.

## 3. Blocking

The blocking config is `CONFIG` in `src/blocking.py`. Blocking **stores unpruned candidates**, and the
pipeline applies `prune()` (`PRUNE` in the same file) when it reads them, so pruning can be re-tuned
without re-blocking. The pruned set is what the model scores and what goes into `candidate_pairs.tsv`.

Each output is a folder of parquet parts (`data/cache/<name>/`, one part per country and 200k query
records). If a run is interrupted, rerun the same command and finished parts are skipped. Progress and
ETA go to `logs/blocking_<name>.log`. After changing `CONFIG`, add `--fresh`, because a run refuses to
mix parts built with different configs.

| Command | What it does | Time | Peak memory |
|---|---|---|---|
| `python -m src.blocking dev --fresh` | Dev slice candidates -> `data/cache/cands_dev/` | ~1 min | ~2 GB |
| `python -m src.eval_blocking` | Dev variants, calibration, pruning sweeps, real-density val analysis -> `docs/blocking_report.md` (needs the three runs below for its last sections). The dev tables are superseded by the real-density section | ~20 min | ~6 GB |
| `python -m src.blocking test` | **Test candidates** -> `data/cache/cands_test/` (99.4M stored pairs; ~4.8 per record after pruning) | 22 min measured (33 min on a hot laptop) | 5.2 GB |
| `python -m src.candsets val` | Val-matched records + 20% of other records against the full train S1 index, labelled -> `data/cache/cands_val.parquet` (33.3M pairs, 15.9M after pruning) | 18 min blocking + ~8 min labelling | 5.4 GB |
| `python -m src.candsets trainsample --train-frac 0.7` | 70% of train-matched and never-matched records against the full train S1 index, labelled -> `data/cache/cands_trainsample.parquet` | ~27 min blocking + ~10 min labelling | ~5-6 GB |

Run them one at a time, with at least ~8 GB of memory available (Task Manager, "Available") and sleep disabled. The top-k search is memory-bandwidth bound, so two jobs slow each other
down more than they gain. All three full runs back to back:

```
python -m src.blocking test && python -m src.candsets val && python -m src.candsets trainsample --train-frac 0.7
```

To follow a long run: `Get-Content logs/blocking_cands_test.log -Wait -Tail 5` (PowerShell) or
`tail -f logs/blocking_cands_test.log`.

Reading candidates in later stages:

```python
from src.blocking import read_cands, prune
test = read_cands("cands_test", pruned=True)          # pruned = the set the model scores
import pandas as pd
val = pd.read_parquet("data/cache/cands_val.parquet")  # columns: label, keep (= survives pruning), weight
val = val[val["keep"]]
```

## 4. Matcher, decision layer and submission (Pass 4)

No train sample: the model trains on half of the **pruned validation candidate set** and is evaluated on the
other half. `src/valsplit.py` splits by query record (a record keeps all its candidates): val S1 ids are shuffled
into halves A and B (seed 42); records of A S1s train, records of B S1s evaluate, and the sampled other records
are split 50/50 (seed 42). Macro F0.5 is scored over the half-B S1 ids only. Every command starts an in-process
memory guard that exits cleanly (code 3) when available memory drops below 1,500 MB (raised from 800 MB in Pass 5 so it
stops a job before Claude Code's own low-memory stop does); all outputs are written to
`.tmp` and renamed, so a stopped run leaves nothing half-written.

| Command | What it does | Time | Peak memory |
|---|---|---|---|
| `python -m src.valsplit` | Split lists -> `data/splits/valsplit_*` and pruned, side-tagged val parts -> `data/cache/val_pruned/` (7.95M train-side, 7.91M eval-side pairs) | 38 s | 1.3 GB |
| `python -m src.matcher features val` | Pair, blocking and context features for the 15.9M pruned val pairs -> `data/cache/feats_val/` | 14.1 min (RA's 27 features; 3.6 min with the Pass 4 stub) | 4.0 GB |
| `python -m src.matcher train` | LightGBM on the train side, negatives subsampled at `NEG_RATE` = 0.5 (early stopping on 10% of its records, not subsampled) -> `models/lgbm.txt`, `docs/feature_importance.md` | 5.6 min | 3.8 GB |
| `python -m src.postprocess sweep` | Scores the eval side, sweeps t, picks it on corrected F0.5 -> `models/threshold.json`, `docs/matcher_report.md` | 4.6 min (30 s when predictions are cached) | 3.7 GB |
| `python -m src.postprocess tune` | Pass 8 decision rules on the cached eval predictions (`data/cache/pred_eval.parquet`, no rescoring): threshold t, b second chance (t2), c relative margin (t3, m), d per-S1 cap (k), every subset tuned jointly with t on corrected F0.5; a rule is adopted only if it earns >= 0.001 -> `models/decision.json`, `docs/decision_report.md` | 4.4 min (1,045 rule sets) | 3.5 GB |
| `python -m src.postprocess errors` | Up to 3,000 false positives + 3,000 false negatives under the adopted rules (`decision.json`, else t) -> `docs/errors_val.csv` (Pass 5: all 2,407 FPs) | 30 s | 3.8 GB |
| `python -m src.run_pipeline test` | Pruned test candidates -> features -> model -> decision (`models/decision.json` rules, else `threshold.json` t) -> `output/matching_results.tsv`, `output/candidate_pairs.tsv`. Resumable: per-part predictions in `data/cache/pred_test/` are reused while the model, features.py and normalize.py are unchanged; with every part cached it only redoes the decision and the writing (1.4 min, 3.2 GB, Pass 8) | ~65 min with RA's features (3 runs: France 8.5, India 1-20 28, rest 28.1; decision 0.5, writing 0.5); 33 min with the Pass 4 stub | 3.7 GB (norm records loaded 8 parts at a time, `NORM_GROUP`); 4.7 GB when a whole country was loaded |
| `python utils/validate_submission.py --matching output/matching_results.tsv --candidate output/_none.tsv --test-dir dataset/test [--check-ids]` | Organizer validator on the matching file | 11 s / 25 s | 1.5 / 2.4 GB |
| `python -m src.check_candidates [--check-ids]` | Same rules for `candidate_pairs.tsv`, streamed (see below) | 21 s / 41 s | 1.2 / 2.1 GB |

The organizer validator with `--candidate output/candidate_pairs.tsv` holds all ~47M candidate ids in Python sets
and passed 7.5 GB before the memory guard stopped it, so on a 16 GB laptop validate the candidate file with
`src.check_candidates` instead. The validator falls back to `output/candidate_pairs.tsv` whenever that file
exists, so pass a path that does not exist to skip it.

Memory notes: `matcher train` peaks while building the LightGBM datasets. With all negatives (Pass 4, 7.2M rows x 55
features) that was 4.7 GB and was stopped once for low memory; `NEG_RATE` = 0.5 (4.1M rows, Pass 5) peaks at 3.8 GB.
Subsampling shifts the predicted probabilities up, which the threshold sweep absorbs (t = 0.79 in Pass 5). The test run holds the norm records of one
country at a time; India is the largest.

Pass 8 (decision rules, `docs/decision_report.md`): on the Pass 7 eval predictions no rule reached +0.001 corrected
F0.5. The best subset, second chance + relative (t2 0.45, t3 0.2, m 0.15, t 0.86), gained +0.0007 and cost 1.2 points
of singleton accuracy, a risk the eval side understates (it lacks the unqueried singletons). `decision.json` therefore
keeps t = 0.80 alone, and `run_pipeline test` from it reproduces the Pass 7 `matching_results.tsv` byte for byte.
After a retrain: `sweep`, then `tune`, then `run_pipeline test`. `tune` rewrites `decision.json`, and a stale
`decision.json` would override the new `threshold.json`.

### Pass 8c: variants from saved predictions (`docs/pass8c_variants.md`)

Every variant goes to its own folder under `output/variants/`: `matching_results.tsv`, `candidate_pairs.tsv` when
the candidate set grows, `submission_<name>.zip` holding the matching file, plus `summary.json` and `validate.log`.
None of these commands writes `output/matching_results.tsv` or `data/cache/pred_test/`.

| Command | What it does | Time | Peak memory |
|---|---|---|---|
| `python -m src.variants threshold 0.85 t085` | Pass 7 predictions at a stricter t, validated in both modes and zipped | 5.5 min | 3.2 GB |
| `python -m src.chainfix eval` | Chain-name candidate fix on the eval side: new pairs for S1 without candidates (same name_core + first house number), re-scored per affected record, corrected F0.5 before/after -> `data/cache/chainfix_eval.json` | 8.8 min | 4.3 GB |
| `python -m src.chainfix test france` / `india` | The same rule on test -> delta predictions in `data/cache/pred_test_chainfix/<country>.parquet` | 2.6 / 6.9 min | 2.0 / 3.7 GB |
| `python -m src.variants chainfix 0.80 chainfix` | Pass 7 predictions with the delta swapped in, plus the grown candidate file | about 7 min | 3.3 GB |

Both chainfix commands abort unless (a) recomputed blocking columns of 2,000 stored pairs equal the stored ones
and (b) about 300 untouched control records re-featurized the same way reproduce their saved probabilities
exactly. `block_cols` hashes in-process: parallel loky workers held about 2 GB of text copies. Those copies are
invisible to the per-process memory guard, which once left orphaned workers behind after it stopped a run.

After merging a new `normalize.py`: `norm_cache`, then the blocking runs of section 3, then this whole section.
After a new `features.py` only: this section from `matcher features val` onwards.
